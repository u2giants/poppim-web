## 1. The ultimate goal

Help staff turn free-text product comments into structured PM records without asking them to re-read and re-enter the same information. Jev may identify one bounded intent—routine update, blocker/dependency, decision, follow-up reminder, or unclear. It must never post the comment, create a dependency/decision/reminder, change priority, or mutate any other business data without a human review and confirmation.

Success means the pilot is useful, stays within its predeclared provider budgets, is privacy-approved, recoverable, and safe for every approved user role. Cheap inference is an advantage, not a reason to weaken data handling, evaluation, authorization, or rollback.

## 2. What this application is

`poppim-web` is POP Creations' internal React PIM frontend. It is a public GitHub repository and a static browser application served at `https://pm.designflow.app`. It stores no data itself; signed-in reads and writes go to the shared Supabase project. Database shape belongs to canonical `shared-db`, not this repository.

Relevant runtime path:

1. `TaskDetailModal` shows the activity and operations panes.
2. `ActivityFeed` posts free-text comments through `src/features/board/collab.ts`.
3. `OperatingPane` creates dependencies, decisions, and reminders through `src/features/operating/api.ts`.
4. The browser client in `src/lib/supabase.ts` carries the signed-in Supabase session.
5. A new app-owned, separately deployed Deno gateway will be the only TypeSafe caller; the browser will never receive the provider credential.

## 3. What triggered this work

The repository-wide Jev audit in [`bugs.md`](bugs.md) found one strong fit: activity triage. Comments contain judgment-heavy text, while the target actions are a small closed set. TypeSafe describes Jev as a typed decision model that returns probabilities/confidence for `Choice`, `Score`, and `Noul` primitives, not a text generator. The vendor currently advertises $0.042 per million input tokens and unmetered output, but explicitly acknowledges that a type-correct decision can still be wrong.

There is no production incident to reproduce. The current friction can be observed by posting an update and then separately opening Operations to create a dependency, decision, or reminder. The pilot addresses that duplicate interpretation work.

## 4. Scope

### In scope

- Newly created product comments only; no automatic historical backfill.
- One five-way kind decision: `routine_update`, `blocker_dependency`, `decision`, `follow_up_reminder`, `unclear`.
- Deterministic server-side minimization/redaction before vendor submission.
- Strict response validation and confidence-based abstention.
- A human review card with editable fields and explicit Confirm or Dismiss.
- Governed non-AI comment/dependency/decision/reminder create/update RPCs so ordinary staff and feature-off rollback do not rely on current administrator-only direct table writes.
- Existing dependency/decision/reminder record shapes.
- Durable idempotency, rate limiting, result recovery, review outcomes, and cost/latency metadata without raw prompt text.
- Separate calibration and held-out evaluation, plus blinded production sampling that includes shown and non-shown results.
- Isolated preview-first deployment, live signed-in proof, and one-step feature rollback.

### Out of scope

- Automatic business writes, automatic priority changes, or autonomous routing.
- Summaries, generated prose, suggested due dates, or generated titles. Jev does not generate text.
- Files, images, emails, links, customer/licensor identities, full product history, or unrelated comments in the vendor payload.
- Replacing deterministic validation, permissions, dates, filters, counts, or database queries with AI.
- A generic AI platform, batch classification of the backlog, or integration into other POP applications.
- Any schema, policy, RPC, index, or grant authored in this repository.

### Security/governance facts that change the design

- `app.comment.created_by_profile_id` is nullable and has no default; the current insert does not set it.
- Current generic `app.comment`, `app.activity`, and `app.notification` writes are administrator-only under RLS. A staff-safe pilot cannot rely on direct inserts or a generic activity cache.
- `app.activity` has no uniqueness contract for an atomic Jev cache. Read-then-insert would race, and accepting a suggestion before recording its outcome could duplicate records after an ambiguous response.
- Root `supabase/**` is deliberately classified as `shared-db` by `.ai-devops/task-gates.json`; app-owned server source must not be placed there or disguised as schema work.
- The repository is public. Real comment text, comment IDs/labels, provider responses that echo text, and secrets must stay outside Git and GitHub.

## 6. Findings and root cause

1. Jev's closed typed decisions match classification, not generation. The target workflow needs a label and probability, while the user supplies the actual record text.
2. The useful gap is after comment creation: staff must interpret the same comment again to decide whether to add an operating record.
3. Browser integration is unsafe because a `VITE_*` credential is public. The provider call needs an authenticated server boundary that is not automatically injected with a shared-database administrator credential.
4. Typed output eliminates invented schema values, not semantic mistakes. POP-specific examples and abstention thresholds are mandatory.
5. Privacy risk is in the prompt, not the result. Product titles and raw context add unnecessary identity; deterministic minimization must happen before the provider call.
6. Regex redaction cannot guarantee removal of every business name. Even after redaction, sending real comments requires an explicit owner/privacy decision on the current agreement, including its perpetual Customer Data processing license for telemetry derivation and unrestricted telemetry use, plus retention/deletion, DPA, and subprocessor terms.
7. Durable correctness requires a purpose-built shared contract: authorship, rate limiting, idempotent attempts, recovery, and atomic human acceptance cannot be bolted safely onto the current generic tables from the browser.
8. A useful launch metric cannot rely only on Accept/Dismiss. That measures shown suggestions but misses false negatives. Blinded labels must include a sample of comments for which no suggestion was shown.

## 7. Approaches considered and rejected

### Direct Jev calls from React

Rejected because the credential and raw request would be exposed in the browser bundle/network. The browser sends IDs only; the server re-reads authorized data.

### Generic `app.activity` cache with no schema work

Rejected after inspection. Non-admin writes are denied, there is no atomic uniqueness contract, and a generic JSON payload cannot safely provide exactly-once acceptance. Shared-db #3298 owns the narrow contract.

### Hosted provider function or root `supabase/functions/**`

Rejected for two independent reasons. The repository gate intentionally routes root `supabase/**` to canonical `shared-db`, and the hosted function runtime automatically receives a broad service-role credential even if application code never constructs an admin client. The app-owned gateway therefore runs as its own least-privilege Deno container under `jev-gateway/`; its environment contains only the public Supabase URL/key, narrow processor identity, TypeSafe credential, HMAC signing secret, and gateway configuration. Gate tests classify `jev-gateway/**` as deployment work while preserving root `supabase/**` as forbidden app-owned schema.

### Raw or “lightly scrubbed” prompt text

Rejected. The server omits product title and unrelated state, replaces common identifiers with typed placeholders, and refuses suspected credentials/private keys/high-entropy tokens rather than attempting a provider call. Owner approval is still required because semantic business names cannot be guaranteed away.

### Real evaluation corpus in `.private/` under the public checkout

Rejected. Gitignore is not an access-control boundary. The single authoritative label/model-result store is the private audited database contract in Step 4: write-only role-specific RPCs, mutually unreadable A/B/model submissions, frozen adjudication, aggregate-only coordinator output, expiry/revocation, and 90-day deletion. Labels, case mappings, and splits are never copied to 1Password, chat, email, or the checkout. A harness resolves one authorized case at a time into protected ephemeral memory/`mktemp -d` mode `0700`, deletes it on exit, and commits only synthetic fixtures and aggregate metrics.

### Automatic creation after a confident label

Rejected because a wrong valid label remains possible. Jev only opens a review form; the user edits and confirms through an atomic RPC.

### One dataset for prompt tuning and approval

Rejected as overfitting. Calibration and held-out cases are frozen separately before results are viewed.

### Accept/Dismiss as the only production accuracy metric

Rejected because absent suggestions have no feedback. Blinded sampling must label both shown and suppressed cases.

### Moving production alias such as `jev-latest`

Rejected because model changes invalidate thresholds. Pin the exact version that passes held-out evaluation and re-evaluate any upgrade.

## 8. Decisions

### Locked decisions

1. Comment creation remains the primary action and never waits for Jev.
2. The five kind labels above are the only output values. Urgency is excluded from the first pilot because it has no independently proven release threshold.
3. `routine_update`, `unclear`, and below-threshold results show no action suggestion.
4. Jev never generates record text or due dates and never writes business data automatically.
5. An authenticated Deno gateway service named `pm-jev-triage` is the only provider caller. It is a separate container/service and must not receive a Supabase service-role key or database login.
6. Product title, files, URLs, emails, identifiers, and unrelated history are omitted from the provider request.
7. The exact evaluated model and versioned question contract are pinned.
8. The server fails open for the comment workflow but shows provider failure separately from a valid no-suggestion result.
9. Shared-db #3298 lands before dependent browser/server code.
10. Human acceptance is atomic and idempotent through the governed RPC; browser direct inserts are not authoritative. The existing manual Operations controls use separate governed RPCs with the same validation and remain available when Jev is off.
11. Real corpus mappings, splits, labels, adjudication, and model results live only in the private audited database store; 1Password contains only named high-entropy secrets/credentials. No real text, IDs, labels, or mappings are stored in the public checkout, chat, or 1Password.
12. A disabled-by-default browser build flag `VITE_JEV_ACTIVITY_TRIAGE_ENABLED=false` removes every Jev suggestion invocation/render path but never the always-on idempotent comment-operation recovery path. A separate gateway flag `JEV_ACTIVITY_TRIAGE_ENABLED=false` refuses provider calls. The server-owned `PIM_JEV_ACTIVITY_TRIAGE` switch controls whether new comments enter the pilot, but eligibility also requires the comment RPC to carry the exact approved disclosure version baked into and visibly rendered by that browser build. All four gates—browser, gateway, server, and disclosure-version match—must pass to enter the pilot; disabling or mismatching any one stops that layer/path, while the documented rollback disables and verifies all three feature flags without removing safe comment recovery.

### Implementer judgment within constraints

- Exact question wording and thresholds, only as supported by the frozen calibration/held-out evidence.
- Direct REST versus an official Deno-compatible SDK; prefer direct `fetch` if the SDK adds Node/runtime complexity.
- Visual placement inside the activity pane, provided it is visibly optional, keyboard accessible, and does not move or hide the posted comment.
- Provider timeout, lease margin, and one-send terminalization based on preview latency/vendor limits; all remain server-owned configuration. Request/token/cost/concurrency ceilings are not implementer choices and stay fixed by owner decision 7.
